# ADR-0016 · 网易云的加密层不进 `core/`，由一个兼容服务承担

- **状态**：已接受
- **日期**：2026-10-20
- **关联**：`docs/abstraction-layer.md` 第 3.3 / 6 节；`docs/requirements/core-music.md`；ADR-0011、ADR-0014

## 背景

网易云的 web 接口要过一层请求加密（`weapi` 的 AES + RSA，`eapi` 的另一套）。
抽象层第 3.3 节的端口里没有"加密"这个概念的容身之处，所以问题变成：
**这层加密住哪儿？**

1. 住进 `core/music/netease.ts`：把公开实现里那套 crypto 抄进本项目；
2. 住进一个**兼容服务**（NeteaseCloudMusicApi 那类）：`core/` 只当一个 HTTP 客户端；
3. 住进 Electron 主进程（`main/`），内核通过第三个端口拿它。

## 决策

**选 2。** `core/music/netease.ts` 是一个**纯 HTTP 客户端**，`baseUrl` 指向任意 NeteaseCloudMusicApi 兼容服务。
`core/` 里没有任何 crypto、没有任何密钥常量、没有对某个具体服务的编译期依赖。

三条配套：

- **响应映射是我们自己的**（`toTrack` / `resolve` 的字段挑选），所以"换一个兼容服务"最坏情况是改映射，
  而不是重写。
- **`recommend` 的两级退让**：有场景词走 `cloudsearch`；没有才走 `/recommend/songs`（要登录），
  失败退到 `/personalized/newsong`（公开）。日推是**账号**级推荐，它听不懂"今晚想听慢一点的"。
- **`resolve` 只试一个档位**。逐档下试是 `MusicSourceChain` 的职责 ——
  源自己降级会让"到底降了几档"变得不可观测，而 `DEGRADED` 徽标要说清楚的就是这件事。

## 后果

- **好处**：`core/` 零加密依赖、可测（假 fetch 就能测穿映射与退让）、可换服务（改一个 baseUrl）。
- **好处**：证书 / 反爬 / 接口变更这些**会烂的事**被隔离在一个可以单独替换的组件里。
- **代价（必须说清楚）**：这个兼容服务是**使用者需要自己准备**的一个外部进程。
  也就是说 v1 的"下载 exe 就能跑"在**音乐源这一环**上并不闭环 ——
  没有网易云 cookie / 没有兼容服务时，电台退到本地音乐目录（`LocalSource`）继续工作。
  这条差距写在 `README.md` 的接入说明里，不藏。
- **重新打开的条件**：出现"必须开箱即用、不许用户起第二个进程"的需求时，
  再评估把最小可用的加密实现搬进来（那时先写 ADR，再动代码）。

## 被否决的选项

| 选项 | 否决理由 |
|---|---|
| 把公开实现的 crypto 抄进 `core/music/` | 抄进来的是**会烂**的东西（密钥、算法、反爬对策），而且它和我们自己的抽象没关系；一次上游变更要动内核 |
| 加密层放 `main/`，内核拿第三个端口 | 端口必须有第二个真实实现（第 9 节）。这里没有"第二种加密"，多一个端口只是多一层 |
| 直接不接网易云，只做本地文件 | 参考源的产品体验一半在"能搜到想听的歌"上；本地兜底是**降级手段**，不是产品 |
| 走官方开放平台 / OAuth | 为 v1 引入一条完整的授权链路，收益只是"少粘一次 cookie"（ADR-0011 已做过同样的取舍） |

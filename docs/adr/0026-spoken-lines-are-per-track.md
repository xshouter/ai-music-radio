# ADR-0026 · 口播按曲目挂起来：跟着这一轮一起生成，切到那首歌才说

- **状态**：已接受
- **日期**：2026-10-20
- **关联**：`core/radio.ts`、`core/brain/index.ts`、`core/prompt.ts`、`shared/domain.ts`；ADR-0001、ADR-0012、ADR-0024

## 背景

要求是「播放时**在后台生成**下一首的口播、不展示；放完自动切歌时**再输出文本并自动播放**」。
而一次推理（`Show`）本来就一次性产出 `say[]`。所以「预生成」不需要第二条推理路径 ——
需要的是把**生成**和**出场**分开：`say[0]` 立刻说（开场），`say[i]` 属于 `play[i]`。

## 决策

**① 一行对一首歌。** `say[i]` 是 `play[i]` 的入场口播；行数上限跟着曲目上限走（4 → 6）。
**② 开场立刻说，其余挂起来。** `radio` 里一个 `heldSay`（`曲目 id → 那一句`），
  在 `thinkOrStep()` 之后按 `play[1..]` 挂上；`advance()` 切到那首歌时才 `speak()` 它。
**③ 挂的是 id，不是下标。** 用户点队列某一行会跳歌 —— 下标会错位，id 不会。
**④ 历史只记说出口的。** 记历史的动作从 `think()` 搬进 `speak()`：被挂起、还没说的句子不该在历史里。
**⑤ `chat` 不适用。** 对话的回答要一次说完，所以 `chat()` 会把挂起的那份清掉。

## 后果

- **好处**：切歌那一下口播已经在手上（不需要现场等模型），而文本在切歌之前不出现在 feed 里。
- **好处**：`OnAir` 一行没改 —— 它本来就是「一句接一句、没词了就站着等」。
- **代价**：`say` 的语义从「这一段的几句话」变成「每首歌一句」，prompt 与需求文档都要跟着改。
- **代价**：一次推理的行数上限到 6，token 账单比 4 行时略高。
- **已知限制**：队列播到尾（tail）时仍然是「重新推理一份新 Show」，那一路的开场同样只立即说第一句。
- **重新打开的条件**：真要做「跳歌也重新生成那一首的口播」时，`advance()` 之外还要在 `playback(started)` 那条路上补一次；
  那就会引入第二条生成路径，需要再写一份 ADR。

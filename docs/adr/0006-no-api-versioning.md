# ADR-0006 · API 契约不做 URL 版本化

- **状态**：已接受
- **日期**：2026-10-20
- **关联**：`docs/abstraction-layer.md` 第 5 / 7 节；开放问题 6

## 背景

问题是契约要不要写成 `/api/v1/...`。惯例上要，但惯例的前提是"客户端与服务端可以各自升级，会出现错配"。

本项目的事实是：UI 与 server 打在**同一个 Electron 进程**里，永远同版本发布。
v1 只有这一个客户端（ADR-0007），连"浏览器版本可能落后"这种情形都不存在。

## 决策

**不版本化。** 契约的唯一真相是 `shared/api-types.ts`，一致性由**契约测试**保证：
mock 一份、真 `core/server.ts` 一份，两份夹具断言的是**同一份契约**（v1 的实际做法，见抽象层第 7 节第 4 步）。
（原文写的是「同一组断言同时打两边」—— 收尾审计时改成事实：mock 独有的控制面在真 server 上不存在。）

## 后果

- **好处**：路径短；没人会因为忘写 `v2` 而调错；改契约只需改一处类型，编译器会指出所有受影响的地方。
- **代价**：将来若真出现"服务端独立部署 + 老客户端还在跑"，要一次性补上版本化。这是一次性的、可承受的债。
- **重新打开的条件**：出现**第二个远端客户端且无法与 server 同步升级**时——例如把 server 挪到云上给别人用。

## 被否决的选项

| 选项 | 否决理由 |
|---|---|
| 现在就用 `/api/v1` | 为不存在的场景付成本；只有一个版本时 `v1` 只是噪音 |
| 用请求头传版本号 | 同上，而且更难在浏览器里直接调试 |

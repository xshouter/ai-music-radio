# ADR-0024 · 日表是开场的来源：一天排一次，大脑靠 `today_plan` 取它

- **状态**：已接受
- **日期**：2026-10-20
- **关联**：`core/radio.ts`、`core/brain/index.ts`、`core/plan.ts`、ADR-0006、ADR-0015

## 背景

`buildDayPlan` 早就把一天拆成三个时段排好，也存进了 `plan` 表 —— 但**整条链路里没有一个人读它**。
它唯一的出口是 `/api/plan/today`（给 UI 看），而真正要「唱」这件事的大脑看不见它：
`PromptContext` 里虽然有 `plan`，可它只在 HTTP 路由里被喂进去过，`boot()` 走的那条路是空的。

于是「今天的第一首歌」这件事根本不存在：每天开机，DJ 都是**现编**一批歌，和早上排好的那份日表无关。
第 26 条把这条记成了缺口。

## 决策

**把日表变成开场的唯一来源，分两半：**

**① 排的时机只有一个：`boot()` 里、`thinkOrStep('schedule')` 之前。**
新增 `ensureTodayPlan()`：`activePlan(今天)` 存在就复用，不存在才 `buildDayPlan` + `savePlan`。
**一天只排一次** —— 否则每开一次窗口，「今天的歌单」就换一批，那就不是「今天定下的」了。
排不出来（音乐源挂了）只 `warn`，**不抛**：大脑还能自己挑歌，只是开场没有「早上定下的那首」可指。

**② 大脑多一个只读工具 `today_plan`（第 5 个）。**
返回当天日表摊平去重后的曲目；日表里存的是 `TrackRef`，补上 `source` 才是一首完整 `Track`（ADR-0006）。
日表为空时给 `{ tracks: [], note: ... }` —— **「还没有」是结果，不是错误**，大脑据此自己挑歌。

工具集合仍然是**封闭**的（ADR-0015）：从 4 个变 5 个，这条规则本身没变。

## 后果

- **好处**：开机第一档有据可依 —— 「我早上挑的那首」第一次真的存在了。
- **好处**：日表只有一个写入口（`ensureTodayPlan`），不会出现两份「今天的歌单」。
- **代价**：`boot()` 多一次串行等待（排表要问音乐源）。排表失败不影响开机，但开场会退化成现编。
- **重新打开的条件**：真要做「跨天常驻」（凌晨 2 点后仍算前一天）时，`localDateKey` 的切日规则要单独定，再写一份 ADR。

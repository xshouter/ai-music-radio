# ADR-0025 · 歌单读成口味画像：机器只写 `taste.md` 这一个名字

- **状态**：已接受
- **日期**：2026-10-20
- **关联**：`core/taste.ts`、`core/music/netease.ts`、`shared/ports.ts`、ADR-0004、ADR-0016；`docs/requirements/core-music.md`、`docs/requirements/core-taste.md`

## 背景

开机的第一步是「这个人喜欢什么」。v1 里这件事只有两条路：人手写 md、点 ♡ 记一笔 —— 都是**冷启动**。
听众的真实偏好在**他自己的歌单**里，而那只有音乐源读得到。

这个需求撞上了两条已经写下来的决定：

1. `MusicSource` 端口在需求文档里写着「**已冻结，不改**」，并列在「明确不做」里的还有「不做歌单」。
2. ADR-0004：「人写的语料在磁盘、系统的结论在库，**两边永不互相写**」。而这里要求**系统写一份 md**。

## 决策

**① `MusicSource` 加第四个方法 `library(limit): Promise<Track[]>`。**
它读听众自己的曲库，**只给口味分析用，不参与播放**（播放走 `resolve`，队列走 `recommend` / `search`）。
放在别处等于再写一个网易云客户端：cookie、兼容服务地址、字段映射都在音乐源这一层。
**「冻结」冻结的是方法集合的形状，不是「永远不能加」** —— 加它要写一份 ADR，就是这份。
拿不到（没 cookie / 服务不在 / 歌单空的）回 `[]`，不抛错，与另外三个方法同一套规矩。

**② ADR-0004 的「永不回写 md」修订为：按文件名分所有权。**
机器**只写 `taste.md` 这一个名字**，人的语料用别的名字（`mine.md` / `notes.md` / 随便）。
`appendLearned()` 仍然只写库 —— 那条纪律没有放松，放松的只是「哪些文件属于机器」。

**③ 触发点只有一处：`saveSettings()` 里 cookie 从「没有」变「有」。**
后台跑（不 `await`）：分析要等音乐源和模型，慢；而设置存完就该立刻生效。
**已经有一份 `taste.md` 就不覆盖** —— 那可能是人自己改过的。

## 后果

- **好处**：冷启动第一次就有东西可读。「这个人喜欢什么」不再是一句空话，而是从他自己收藏里读出来的。
- **好处**：`read()` 一行没改 —— 生成的那份就是语料目录里的一个 md，Profile 和大脑自动看见它。
- **代价**：端口的语义变宽了一层（多一个「只读、不播放」的方法）。代价写在文档里，不在代码的注释里。
- **代价**：多一次模型调用（首次填 cookie 那一下）与一次歌单读取（最多 10 张歌单）。
- **重新打开的条件**：真要做「歌单浏览 UI」时，`library()` 的返回不够（要歌单名、封面、分页）——
  那时该加的是**新的端口**，不是把这个方法撑大。

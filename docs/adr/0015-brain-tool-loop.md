# ADR-0015 · 大脑是自建 tool loop，工具集合封闭，`emit_show` 是唯一出口

- **状态**：已接受
- **日期**：2026-10-20
- **关联**：`docs/abstraction-layer.md` 第 3.1 / 3.7 节；`docs/requirements/core-brain.md`；ADR-0008、ADR-0012

## 背景

端口层（第 3.1 节）已经定死：**provider 只负责一次补全**，不负责工具循环。
`Brain.think(input): Promise<Show>` 是"一次推理的产物"，所以循环必须住在 `core/brain/` 里。

那就有三种写法：

1. 用某家 SDK 的 function-calling 编排（自己不用写循环）；
2. 用某家的"结构化输出 / response_format"直接把 `Show` 抠出来，不要工具；
3. 自己写循环，把工具**当成**会话的一部分。

## 决策

**选 3，自建循环**（`core/brain/index.ts` 的 `ToolLoopBrain`）。四条具体规则：

**① 工具集合是封闭的，只有四个。** `recommend_tracks` / `search_tracks` / `recent_plays` / `emit_show`。
加一个工具＝改这个文件 + 补一条测试，而不是让模型自己"想"还能干什么。

**② `emit_show` 是唯一出口。** 只有它能把一次推理结束成 `Show`。
步数预算默认 6，**最后一步强制** `tool_choice = emit_show` —— 与其在预算耗尽后抛错，
不如给它一次"必须定稿"的机会。

**③ 校验是硬的，并且驳回理由会回到模型手里。**
- `say` 至少一句；`reason` 必须有；`play` 3–6 首。
- **曲目 id 必须是本轮某次工具真的返回过的**（`registry` 是执行点）。
  这条是"抓需求"的落点：一个会推荐不存在歌曲的 DJ 不是 DJ。
- 驳回时的理由原样作为 tool 结果送回去（"unknown track id(s) [...]"），
  **这是自愈的唯一入口** —— 模型看到的是"哪一条错了"，不是"你错了"。

**④ 工具失败是结果，不是崩溃。** 音乐源挂了 → 把 `{error: 'MUSIC_SOURCE_UNREACHABLE'}`
作为 tool 结果交回去，模型有机会换工具、换说法；而不是让整轮推理炸掉。

配套：人设与"怎么说话"（英文、1–3 句、不许自称 AI、不许念歌单）写在 `core/prompt.ts` 的代码里，
**不做成配置** —— 它是产品的一部分，不是运维参数。

## 后果

- **好处**：换厂商＝换一个 provider 文件，大脑不动；"什么时候停"这个产品脾气握在自己手里；
  每次推理的工具轨迹（`onStep`）可观测，测试直接断言它。
- **好处**：协议翻译的错误面被压到两个文件里，而且可以用脚本化的 HTTP 假身测穿，不必联网。
- **代价**：要自己维护两套厂商写法的翻译（`tool_calls.function.arguments` 是**字符串**、
  Anthropic 的 tool 结果要**合并进**一条 user 消息），以及自己兜底解析。
- **已知限制**：`BrainInput` 里没有 `signal`，所以一轮推理暂时不可取消；
  `emit_show` 之外还认"JSON 写在正文里"（走**同一套**校验），这是给不用工具的模型的兜底，不是主路径。

## 被否决的选项

| 选项 | 否决理由 |
|---|---|
| 用厂商 SDK 的编排循环 | 两家的 `tools` / `tool_calls` / `tool_use` 写法完全不同；把"什么时候停"交给某家的默认值 = 把产品脾气外包 |
| 用"结构化输出"抠 `Show`，不给工具 | 那就没有推荐这件事了：DJ 没法先看看歌单、再决定；工具是"抓需求/抓场景"的落点 |
| 允许大脑直接写 `Store`（自己记账） | 写入端只有一处（server 的 `/api/playback` 与 `/api/feedback`）。大脑自己写会造出第二条路径，统计立刻不可信 |
| 不校验 id，失灵了再修 | 会静默播出一首不存在的歌；校验的第一顺位是**闭集**，不是容错 |
| 把 `emit_show` 之外的工具也放开给模型自由加 | 工具越多，模型越倾向于多绕几圈；四个工具刚好覆盖"看图 → 定稿" |

# ADR-0017 · 口播的词时间戳从音频真时长推，不依赖 provider

- **状态**：已接受
- **日期**：2026-10-20
- **关联**：`docs/adr/0012-spoken-line-payload.md`（`SpokenLine.words` 的形状）、`docs/adr/0008-tts-fish-audio.md`、`shared/ports.ts`（`TtsProvider`）、`core/tts.ts`、`docs/requirements/core-tts.md`

## 背景

ADR-0012 定了 `SpokenLine.words`（词级时间戳）的形状，并写了兜底："给不出时退化成『一个覆盖全句的词』"。

4.4 落地时核实了 Fish Audio 的真实接口：`POST /v1/tts` 直接回 **mp3 字节**，响应里**没有**任何对齐 / 时间戳字段。也就是说，ADR-0012 写下的那个兜底就是常态，不是例外。

两条路：

- 照字面执行 —— 每个 `SpokenLine` 都只给一个覆盖全句的词。UI 永远整句高亮。
- 让词时间戳**从音频本身推**。

## 决策

`core/tts.ts` 从**真实音频**推词时间戳，分两步：

1. **总长是真的**：`mp3DurationMs(bytes)` 只读 mp3 帧头（MPEG1/2/2.5 的 Layer III）累加时长，跳过 ID3v2 前缀，**不解码**。这是音频的客观长度。
2. **逐词边界按文本长度比例分配**：权重与 mock 同一套（短词 >= 0.6、长词封顶 2.4），按累积比例把总长切开；**末词一定收在真实总长上**。

边界：

- 只有在总长拿不到（`<= 0`，比如远端回的是不可解析的字节）时才退化成一个覆盖全句的词 —— 那才是 ADR-0012 说的兜底场景。
- `words` 是相对这一句音频起点的毫秒，**不改** ADR-0012 定的形状。
- 分配逻辑是**纯函数**（`wordsFor`），可以单独测；它不碰网络、不碰 fs。

## 后果

- **好处**：
  - 口播进度条的总长与音频**同源**，不会出现"词走完了声音还在放"—— 这正是 ADR-0012 最担心的露馅点。
  - 逐词高亮有真实的总长兜底，比"整句一起变色"好看一档。
  - 将来换一个**真会给 alignment** 的 provider 时，只需要在那一层把词表填进 `TtsResult`，`wordsFor` 退居兜底 —— 形状不变。
- **代价**：
  - 逐词**边界是估算**，不是口型对齐。英文里长短词混排时，某个词的起止可能与声音差半拍。诚实地说：这是"看起来对"的高亮，不是"逐帧对"的高亮。
  - 多了一个 mp3 帧头解析器（约 40 行 + 一条测试）。它认 MPEG1/2/2.5 Layer III；别的编码认不出来就给 0，走兜底，不会崩。
- **重新打开的条件**：接入一个**真会给词级 alignment** 的 provider（Fish 之外的），届时 `wordsFor` 只做兜底。

## 被否决的选项

| 选项 | 否决理由 |
|---|---|
| 严格照 ADR-0012 字面：永远一个覆盖全句的词 | 形状对，但白丢了已经能拿到的真实总长；UI 永远整句高亮，比逐词难看 |
| 让 UI 自己按字符数估时长 | 与音频不同源 —— 正是 ADR-0012 明文否决过的做法 |
| 引用一个 mp3 解码库拿时长 | 为了一个总长拉进一个解码器 + WASM，收益不抵成本；帧头就够了 |
| 在前端用 `<audio>.duration` 兜底 | 前端只跟后端说话（铁律 5）；进度条真相只能有一处，在后端 |

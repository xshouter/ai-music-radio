# ADR-0035 · 现场日志：双击之后出了什么事，事后要能读出来

- **状态**：已接受
- **日期**：2026-10-21
- **关联**：`main/log.ts`（新增）、`main/main.ts`、`main/bootstrap.ts`、`main/netease-service.ts`、
  `tests/main/log.test.mjs`；ADR-0028、ADR-0034
- **需求**：`docs/requirements/diagnostics-log.md`

## 背景

发出去的便携版是**双击启动**的。也就是说 `main/` 里那一排 `console.warn` / `console.error` 写给了
一个**没有人看的地方** —— 开发态终端里看得见的那几行，发布之后全部消失。

能留在现场的三样东西都不够用：

- 界面上的聊天区只留**最后一条**错误的 code + message（ADR-0027）。历史、上下文、以及
  「它到底往哪儿发了请求」都不在里面。
- `%APPDATA%\EdgeRunner\` 下的 sqlite 只有**结果**（消息、播放、日表），没有**过程**。
- 第 48 条那次「我打开是这样」：真正花时间的不是修，是**重建现场** —— 数落点里的文件、
  把 prefs 从 sqlite 里读出来、再拿同一把 key 分别打两个域名。这些事本该看一眼日志就完。
  而那一次之所以要重建，恰恰因为唯一能指路的那句话（上游原话）在界面上被丢掉了（ADR-0034）。

## 决策

**① 落在 `main/`，`core/` 一个字不改。**

日志要写文件，而 `core/` 不许碰 `node:fs`（铁律 5 的同一套理由：`core/` 只在抽象层上说话）。
更重要的是，「日志放哪、留多久」是**宿主**的决定，不是内核的。所以 `core/` 继续只用它的 `warn` 说话。

那为什么包一层就能全记上？因为 `core/` 的**每一次**出网都经过同一个端口 `HttpFetch`
（大脑 / 音乐源 / TTS 三条路，ADR-0008 与 ADR-0016 定的）。在 `main/` 把它包一层，等于全部记上。

**② 一行一条，格式固定。**

`<ISO 时间>  <区域>  <正文>`，区域是 `boot / http / error / warn / music` 五个词。
人类可读，前缀稳定（grep 与解析都不难）。多行正文（上游那一整页 HTML 报错）**先压成一行再截断**（400 字）。

**③ 去敏是结构性的，不靠猜 key 的形状。**

- **请求头一律不记。** key / cookie 都在头里；不记头，就没有它们。设置摘要只记「set / 空」，长度都不记。
- URL 里**已知名**的 query 值换成 `<redacted>`：`cookie / token / api_key / key / sign / session /
  password / authorization`。这是白名单式的结构性保证，不是「看起来像 key 就过滤」——
  猜形状的过滤总有漏的（ADR-0011 那把 cookie 就不像任何 key 的形状）。

**④ 单文件上限 1 MB，超了改名成 `.1`（只留一代）再开新的。** 常驻应用不能无限涨；
更久以前的事，价值低于它的维护成本。

**⑤ 连锁事都要说话。** 第 48 条暴露的另一件事：内置服务（ADR-0028）**跑着跑着死掉是静默的** ——
原来只有「启动失败」会 warn。现在进程一退就带一句，连子进程自己的最后三行。

**⑥ 非 2xx 时，读过响应体之后要换一个能再读的响应回去。**

这一条不是设计，是**踩出来的**：要把上游原话记下来就得读一次 `response.text()`，而 body 只能读一次。
原来的对象还回去，`core/` 那边 `HttpError.detail` 一读就撞 `Body is unusable` —— 上游一句好好的
`Incorrect API key provided` 会被换成一个 `TypeError`。所以包一层之后要把 `{ status, text, bytes }`
**重建**一份再交出去。`tests/main/log.test.mjs` 的最后一条就是钉这个回归的。

不适用的情况：要看的东西不在 `HttpFetch` 上（渲染进程的错误、崩溃），或者要从别人的机器上收日志。
那需要另开一条路，本决策不管。

## 后果

- **好处**：事后能读；随手把日志转给别人也不泄露（这是它敢被发出去的前提）；`core/` 零改动；
  ADR-0034 那一类问题从「重建现场」变成「看一眼文件」。
- **代价**：`main/` 多一个文件、十九处接线；日志与代码会漂移 —— 记下来的话和实际做的事不一致，
  只能靠人盯着。写失败**一律吞掉**（日志不许把电台弄挂），所以「日志没写下来」本身也是静默的。
- **重新打开的条件**：出现「要在界面里看日志」「要按等级开关」「要从别人的机器上收」——任何一条
  都说明一个文件不够用了。

## 被否决的选项

| 选项 | 否决理由 |
|---|---|
| 在 `core/` 里记 | `core/` 不许碰 `node:fs`；而且「放哪、留多久」是宿主的决定，不该进内核 |
| 继续靠 `console` | 便携版双击启动，stderr 通到没有人的地方 |
| 记请求头 / 请求体 | key 与 cookie 都在头里；请求体可能是一整篇提示词。要「用了哪个模型 / 哪个地址」，由 `boot` 那行设置摘要负责 |
| 过滤 key 的形状（正则猜 `sk-…`） | 猜形状的过滤总有漏的。不记头 + 只匿名已知名的 query，是结构性保证 |
| 加 debug / info / warn 等级开关 | 常驻的个人应用，量本来就小；多一个开关就多一条「为什么没记下来」的错路 |
| 暴露成 `GET /api/logs` | 要动契约与令牌（铁律 3）；文件已经够用，而且**应用退出之后它还在** |
| 引 `electron-log` 之类的现成包 | 一次 `appendFileSync` 加一次 `renameSync` 就够；为几十行引一个依赖不划算 |

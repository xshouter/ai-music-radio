# 需求：开机进度（排表那一段的 CLI 界面）（PR #60）

> 铁律 2 的产出。这份文件回答「这一轮被要求做成什么」，**不回答**「怎么实现」（那在 ADR-0032）。
> 来源：用户原话「排表可以做一个cli界面显示进度，排完之后再进入开场口播」。

## 摸底：缝到底在哪

1. **排表挡在开场前**：`core/radio.ts` 的 `boot()` 里 `await ensureTodayPlan()` 在 `await thinkOrStep('schedule')` 之前
   —— 排表本身 14–28s（PR #59 实测）。
2. **更糟的是这 14–28s 里连窗口都还没有**：`main/bootstrap.ts` 的 `startRadio` **await 完 `radio.boot()` 才 return**，
   而 `main/main.ts` 的 `openWindow()` 是**拿到返回值之后才 `new BrowserWindow`**。
   所以当天第一次开机，屏幕上没有这个应用 —— 这不是「界面没显示进度」，是「界面还没出生」。
   进度界面要能做出来，窗口必须先出生；这一条决定了本轮一半的改动量。
3. **进度源是现成的**：brain 的 `onStep`（`ToolStep = { index, tool, args, result }`）每次工具调用后回调一次；
   `providers()` 里它已经接到 `harvest`（`core/radio.ts:237`）。
4. **只有「当天还没排过表」才有这段等待**：`ensureTodayPlan()` 当天已有日表就直接 return、**不发任何事件**。
5. **晚连上的窗口会漏事件**：`subscribe()` 连上时只补推 `now` + `queue` + `state`（+ 可能的 `error`），**不补发 `plan`**。

## 摸底之后补的一条：进度要盖到哪一段结束

进度界面能存在的前提是**窗口先出生**（摸底第 2 条）。由此定死两件事：

- `startRadio` 不再 await 排表；窗口起来、`loadURL` 之后才跑 `boot()`。
- 进度**盖到开场口播真的出声为止**（排表 → 写开场稿 → 合成语音），第一句 `say` 到达即交接口播界面。
  只盖「排表」的话，排完到出声之间还有 10–20s 是空白 —— 那段等待一样难看。

## 行为（冻结）

1. **只在这一段发光**：进度事件只在 `boot()` 期间产生（一个 `booting` 开关）；聊天 / 切歌那些工具调用**一条都不发**。
2. **窗口先出生**：`startRadio` 返回时只保证「服务已在监听」；`boot()` 由 `main.ts` 在窗口 `loadURL` 之后自己发起，
   `StartedRadio` 因此多一个 `boot()`。
3. **进度是累积的、幂等的**：事件载荷带**累积的 steps 数组**，UI 只按它渲染、不自己拼顺序 ——
   晚连的窗口补一条就对齐了，不用重放事件。
4. **步骤 id 是 UX 概念，不是工具名**：`daily-pool` / `recent-plays` / `deep-search` / `draft-plan` / `opening-line`。
   工具 → id 的映射只在 core 里（工具改名不该动契约）。
5. **同一个 id 只出现一次**（去重），按首次出现顺序。
6. **结束条件**：第一句 `say` 出去 → 结束；`boot()` 收尾（含没 key / 排表失败）→ 结束。**界面不许挂住。**
7. **失败只是多一行警告**：排表内部失败不阻塞开机、也不额外弹错（延续 `ensureTodayPlan` 现在的 catch 行为）。
8. **不动的东西**：`ensureTodayPlan` 的「已有日表直接 return」不变；`PlanCurator` / `DayPlan` / `PlanBlock` 一个字不动；
   播放器与口播流水线（ADR-0029）不动 —— 进度只是**多一个观察者**。

## 不做

- 不做真终端窗口、不做命令输入、不做日志落盘。
- 不把 taste 学习（`learnTaste()`）纳入进度（它本来就后台跑、不 await）。
- 不改排表本身快慢（那是 PR #59 的话题）：这一轮只把等待**显示出来**。
- 不做「取消排表」按钮（排表不可中断，v1 不做）。

## 验收

- 单测 `tests/core/radio.test.mjs`：进 `boot()` 后工具调用 → 发 `progress`；steps 去重且有序；
  第一句 `say` 之后 `phase` 变 `done`；没 key 时 `boot()` 收尾也把 `progress` 收成 `done`（**不许挂住**）；
  非 boot 期间（chat / track_end）**一条 `progress` 都不发**。
- 单测 `tests/contract/mock.test.mjs`：mock 也能发 `progress`（契约两边同源）。
- UI：dark / light 都渲染；steps 逐行打勾；结束时淡出并交给口播界面。
- 打包后单跑：当天第一次开机，**先出现窗口**（≤2s 内看到进度界面），再是口播。

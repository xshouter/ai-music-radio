# 需求 · 口播模型：一首歌一条、各是独立消息、只有歌曲介绍算口播

- **状态**：**已冻结**（2026-10-20）。第 5 节的三个问题用户已逐条点头，按我的倾向定案。
- **来源**：用户 2026-10-20 的口头要求 3 / 4 / 5 + 随后三条 yes + 一条补充要求
- **关联**：`core/radio.ts`（`speak` / `holdIntros` / `advance` / `chat`）、
  `renderer/src/hooks/useRadio.ts`（`withSay` / 口播管道）、`renderer/src/components/OnAir.tsx`、
  `renderer/src/App.tsx`（`openOral` / 自动进口播）、`shared/domain.ts`（`SpokenLine`）、
  `core/prompt.ts`（`PERSONA`）；ADR-0001、ADR-0012、ADR-0026、ADR-0029

## 1. 现状（先把「现在到底是什么样」说清楚）

- **后端已经是「一行对一首歌」**：`Show.say[i]` 属于 `play[i]`（ADR-0026）。开场那句立刻说，其余压在 `heldSay`。
- **后端已经「一条消息一行」**：`speak()` 每合一句就 `store.appendMessage(...)`（`core/radio.ts`）。
- 但**界面把它们合并成了一条**：`withSay()`（`useRadio.ts`）把新来的一句叠到上一条 DJ 消息上，
  并把 turns 追加进 `meta.turns`。feed 上看到的是「一个气泡里塞了好几段」。
- **口播的 `<audio>` 只在全屏态里**（`OnAir.tsx`）。主界面上没有任何东西播它 ——
  回到主界面之后到达的口播只有文字、永远不出声。
- **聊天回复和口播共用一套**：`chat()` 也走 `speak()`（`radio.ts`），于是聊天的答复同样拿到 turns、
  同样有 PLAY / REPLAY、同样进全屏口播。

## 2. 要什么

1. **一首歌一条**：口播与曲目 1:1，一条就是一段。
2. **每条是独立消息**：feed 上一条口播 = 一个气泡（一个时间戳、一个入口）。
3. **只有歌曲介绍算口播**：用户与 DJ 的对话不算 —— 不给入口、不进全屏口播、不出声。
4. **切歌时不断流程**（方案见第 4 节）。
5. **口播更丰富、按曲风换腔调**（用户 2026-10-20 补充）：一条写这一首歌本身，
   而且delivery 跟着类型走（ambient 慢、rock 短促、jazz 松弛）—— 详见第 6 节。

## 3. 契约改动

`SpokenLine`（`shared/domain.ts`）加一个来源标记 `kind: 'intro' | 'talk'`，由 `speak()` 的调用方给：

| 调用点 | kind | 表现 |
|---|---|---|
| `thinkOrStep` 的开场句 | `intro` | 逐句；每句一条独立消息；带 turns、带入口、进口播流 |
| `advance()` 推出去的那句 | `intro` | 同上 |
| `chat()` 的回答 | `talk` | **整段合成一条** dj 文本消息；不合成 TTS；无 turns、无入口、不进全屏口播 |

**为什么加真字段而不是塞 `meta`**：「这条是不是口播」会被入口按钮、全屏态、口播管道同时问，
藏在 `meta` 里的隐含约定迟早会错一处 —— 错的那一处正好会让人以为「聊天也能当口播」。

**为什么 `talk` 不合成 TTS**：它不是口播，没有任何界面承接它 —— 合了也没人听，白花钱、白等。

## 4. 切歌时的流程（方案）

核心动作：**把口播的播放权从「全屏态组件」提到 `useRadio` 的一条串行管道上。**

- `useRadio` 里再建一个 `new Audio()`，口播从此**不依赖任何界面**。
- 全屏态（`OnAir`）降级成这条管道的**视图**：打开它不重播、不重置；✕ = 主动停止口播。
- 同一时刻只有一句在说。**切歌 = 换口播，不排队**：新歌那一条一到就顶上当前句，
  **已经过期的介绍直接丢弃**，不补播。
- 介绍还没生成好就切了 → 音乐先走，介绍到了当场接上（不追溯、不排队）。

**为什么不「当前一句说完再切」**：口播和画面会不同步 —— 嘴里讲着上一首，机器已经放了下一首。
**宁可断一句，不要错一首。**

`shortcut:` 顶上当前句是**硬切**（`<audio>.src` 直接换），没有 60–120 ms 淡出 ——
只有在手动连跳时听得出。真要修，在这一处的 src 切换前后加一次 `volume` 斜坡。

## 5. 定案（原开放问题，用户逐条 yes）

1. **聊天回复不出声** —— 只有文字（问题 1）→ `talk`，如第 3 节的表。
2. **切歌时正在说的那句 intro 直接顶掉**，过期的丢弃（问题 2）→ 第 4 节。
3. **暂停音乐时口播跟着停**（问题 3）→ `toggle` / `stop` 同时管两个 `<audio>`。

## 6. 口播的腔调（用户补充）

`core/prompt.ts` 的 `PERSONA` 与 `emit_show` 的 `say` 描述一起改：一条写**这一首歌本身**
（一个声音、一个速度、一个年代、一种情绪），一到两句、30 词以内，并且**delivery 跟着曲风走**：
ambient / downtempo 慢而留白，rock / punk / hip-hop 短促向前，jazz / soul 温暖像聊天，electronic 精确带一点俏皮。
这不是新机制，是同一轮推理里的一行指令 —— 模型已经在写这段文本，只是之前没有风格要求。

## 7. 挂账（用户自己标的待办，尚未开工）

- **每日推荐歌单**：LLM 能不能拿网易云的「每日推荐」来生成今天的歌单（用户问题 5，标为待办）。
- 未修的相邻缺口：`advance()` 点队列跳歌不会重新生成那首的口播（ADR-0026 已知限制）。

## 8. 验收

- feed 上：一首歌一条口播，一条一个气泡、一个时间戳、一个入口。
- 用户提问后的回复：不进全屏口播、没有 PLAY / REPLAY、不合成音频。
- 切歌（自然放完 / 手动跳过 / 点队列某一行）：口播立刻换成新歌那条，不断音、不补播过期的。
- 口播在**开着界面**时跟着音乐一起响；**暂停音乐 = 暂停口播**；✕ = 停止口播并回主界面。
- 口播的写法跟着曲风变，一条是给这一首歌的、不是给整张歌单的。
- 四条机械检查全绿 + 真 app 复测。

> 铁律 2 的产物。状态：**已定案**（grill 第 2 轮收敛），留 **1 处待截图**（见「阻塞项」）。

> `docs/references.md`、ADR-0007、ADR-0008、ADR-0009。

## 目标

把参考界面按 **1:1** 复刻成一个**单窗口 PC 应用**：打开就是一台在播的电台，DJ 在说话，队列在走，
用户能插话点歌、能收藏、能看 DJ 的档案。

两句话概括这一版和上一版的区别：

- 上一版做的是「一个能跑起来的电台界面」；这一版要做的是「**和参考分不出来**的电台界面」。
  本项目的 taste 由它承担——面试官看到的第一眼就是它。
- 顺序上它是 3.1 的**重做**，不是叠加：布局模型换掉（响应式两态 → 固定基准等比缩放），
  歌词整条链路拿掉，补齐歌单 / 喜欢 / DJ 详情 / 口播界面四块。

界面只跟后端说话（HTTP + WS），一行都不碰数据库（铁律 5）。

### 主界面结构（从上到下）

1. **顶栏** — 左：圆形头像（28px，点阵风人像，**点它开 DJ 详情弹层**）+ `EdgeRunner` 点阵 wordmark；
   右：`LOGIN` 胶囊（**点它开凭证弹窗**：LLM / TTS 的 API key + 网易云 cookie）、
   `DARK` / `LIGHT` 胶囊切换（当前态实心深色）。
2. **大钟区** — 点阵大数字 `21:11`（约 96px）；下面 `Monday`；再下面 `28 APR 2026`（灰、小）；
   再下面绿点 + `ON AIR`（宽字距）。降级时 `ON AIR` 旁出现 `DEGRADED`。
   整块背景是**点阵网格**（1px 圆点、16px 间距、底部渐隐）。
3. **运输条** — 左：绿色小频谱 + 曲名（白）+ `— 歌手`（灰）+ `PLAYING` 标签；
   中：`⏮ ⏸ ⏭ ■ ♡` 五个圆键；右：`HIDE` / `LIST` 胶囊、`FAV` 胶囊、`VOL` + 滑杆。
4. **进度** — 两端 `1:01` / `3:14`，中间细线，已播段实心。
5. **QUEUE 区** — 表头左 `QUEUE`（切到喜欢源时是 `FAVORITES`）、右 `N TRACKS`；
   每行 `序号  曲名  …  歌手`（歌手右对齐）。
   **当前行**：左侧 4px 绿条 + `▸` + 曲名与歌手都变绿。
   **两种来源在同一块面板里切换**：`AI 推荐`（`GET /api/next`）与 `FAV`（`GET /api/favorites`）。
   在喜欢源里，悬停（或键盘聚焦）某一行时**行尾的歌手位置被一个 `✕` 替换**，点是取消喜欢——设计说明见下。
6. **DJ 面板** — 表头左 `● EdgeRunner`（绿点 + 名字），右 `LIVE`；表头右侧还有一个**小频谱**（DJ 说话时跳）。
   往下是消息流：系统行居中 `Connected to EdgeRunner server`；DJ 消息左对齐（头像 + `EDGERUNNER` + 气泡 + 时间戳 + `REPLY`）；
   我的消息右对齐（名字 `ME` + 头像在右 + 气泡 + 时间戳）；DJ 消息里的**曲目卡**见下。
7. **输入条** — 输入框 `Say something to the DJ...` + 麦克风图标（v1 只作外观）+ `↑` 圆形发送键。
8. **底栏** — 左 `EDGERUNNER FM`，右绿点 + `CONNECTED`。

**曲目卡**（DJ 消息里）是一个圆角矩形 + 1px 边框，内含曲名 + 歌手：

- 当前正在播的那张：绿色边框 + 绿色 `★` + 曲名绿字；
- 其余的：`▸` + 灰字；
- **点一下就播放**（用户已确认）。

### 喜欢列表怎么删（我设计的，不是复刻的）

用户把这一条交给我定。约束三条：参考界面里行尾**只有歌手、没有任何图标**；删除必须**可逆**（那是用户数据）；
不能为了它新加一块布局。

| 决定 | 值 | 为什么 |
|---|---|---|
| 触发 | 在 `FAV` 源里，悬停 / 键盘聚焦某一行 → 行尾的歌手被 `✕` 替换 | 常驻 `✕` 会让每行右边多一个符号，破坏参考那种「右边只有歌手」的干净；悬停才出现是最小侵入 |
| 符号 | 字符 `✕`，不是垃圾桶图标 | 整个界面没有实心图标（`♡` `■` `↑` `▸` `★` 全是字符或由参考定义），`✕` 属于同一套字符语言 |
| 与「点行播放」的关系 | 两个**不同元素**；点 `✕` 不冒泡成播放 | 一行上两个动作，必须互斥 |
| 误触保护 | 删除后 3 秒内，表头右侧的 `N TRACKS` 变成可点的 `REMOVED — UNDO` | 复用已有的槽位与排版，**零新增布局**；删除是数据损失，不能没有回头路 |
| 撤销后 | 那一行回到列表里 | 不做排序，按 `GET /api/favorites` 返回的顺序插入 |
| 不做 | 二次确认弹窗、拖拽、常驻删除按钮 | 都要新组件，收益为零 |

**波形 canvas 的算式**（我们照抄它的形状，不抄它的代码）：

```
barGap=2, barWidth=2, step=4, count=floor(cw/step)
env = 0.55 + 0.45*sin(center*PI)
amp = live ? (level*0.7 + proc*0.3) : proc      // proc 由三条不同频率的正弦混合而成
h   = amp*env*ch*1.25*waveIntensity + noise*(live?6:12)
h   = max(4, min(ch-4, h))
alpha = 0.55 + 0.4*(1 - (center-0.5)**2*2)
```

**时间主轴是口播，不是音乐**：口播音轨驱动进度、逐词高亮、自动滚动；歌只在下面以 **28% 音量循环垫底**。

> 参考的逐词时间戳是**假的**——它把每句时长按词数均分推出来的。
> 我们用 Fish Audio 的真实 word-level 时间戳（见 ADR-0008），**这一点会比参考更准**。

> 与「UI 文案英文」的关系：参考自己就是**中英混排**（口号中文、座右铭英文），这一处沿用它的混排，

## 3.1 → 3.2 变更记录（每条：改了什么、为什么）

3.1（PR #10）是**已经合并**的版本，不在这个分支上回滚；它在 `main` 上继续存在，直到 UI 重做的 PR 落地。
下面每条都写清「当时为什么那么写」和「现在为什么改」——这份对照本身就是过程证据。

| # | 3.1 的做法 | 3.2 改成 | 为什么改 |
|---|---|---|---|
| 1 | **两态响应式**：宽窗大钟态 / 窄窗卡片态，断点 ~720px，同一个页面折成两种布局 | **单态**：一套布局 + 固定基准尺寸，整块等比缩放 | 用户要求「界面应该是一个合理的长方形，且可以按照固定比例缩放」。响应式两态意味着**永远有一个态不是参考的样子**——而本项目要的是 1:1。把布局钉死、只缩放，才能保证任何窗口尺寸下都是同一个界面。代价：窄窗会出现留白，这是有意的取舍。 |
| 2 | 歌词：`GET /api/lyric/:songId` + 自写 LRC 解析 + 逐行高亮 | **整条链路删除**（PR #15 已落地） | ADR-0009 已定「v1 不做歌词」。它先以**独立的删除 PR** 还掉了：删端点、删 `Lyric` / `LyricResponse`、删 mock 路由、删 `renderer/` 的解析器与派生、删 `tests/renderer/lrc.test.mjs`。拆出来而不是和布局重做混在一起，是为了能单独读懂、单独回滚（铁律 1）。 |
| 3 | 运输条只有 `HIDE` + `VOL` | 补齐 `⏮ ⏸ ⏭ ■ ♡` + `HIDE`/`LIST` + `FAV` + `VOL` | 用户指出参考是一个**完整播放器**，含歌单操作与喜欢的音乐。3.1 只做了「能验证 `say` 逐句浮现」的最小控件，不是播放器。 |
| 4 | 没有 DJ 详情 | 加 **DJ 详情弹层**，点顶栏（或 DJ 面板）头像弹出 | 用户明确要求（交互决策 3）。参考里它的内容很满，是「设计 agent」这件事最直观的展示面。 |
| 5 | 没有口播界面 | 加 **口播全屏态**，规格按线上真源逐条抄 | 用户找到了参考源自己的口播界面，要求复刻。它是这个项目**最像「产品」的一屏**：逐词高亮 + 真波形 + 56 格进度。 |
| 6 | 大钟下面写 `NOW PLAYING` | 改成 `PLAYING` | 对齐截图上的字。 |
| 7 | `EDGERUNNER FM` / `LIVE` 等文案已定，但 wordmark 与取名未定 | `Claudio` → `EdgeRunner`；DJ 名 = 项目名 | 用户已定项目叫什么。 |
| 8 | `plan`（日表）在 Player 上**没有位置**，3.1 留了一个没勾上的验收项 | 仍然**不放进 Player**，去处写进 3.3 的 Profile | 保持 3.1 的判断：参考画面里没有它的位置，就不猜一个界面出来。这一条不因为重做而改变。 |
| 9 | 麦克风按钮只作外观 | 不变 | 交互决策 4：v1 不做语音输入。 |
| 10 | `LOGIN` 不复刻 | **保留**，且点开一个**凭证弹窗** | 我原来按「单机无账号体系」判它没有对应物，判错了：用户指出它该承担「填自己的 API key 与网易云 cookie」这件事——那正是本项目**唯一真正需要输入**的地方。代价：这是 3.1 与 PR #12 都没预留的**新面**，所以它要先补契约（P5）才能动 UI。 |
| 11 | QUEUE 只有一种来源 | **两种来源**（`AI 推荐` / `FAV`），同一块面板切换 | 用户明确「点 FAV 就是把 queue 里的歌换成 fav」。原来的读数（FAV 打开一块独立面板）是错的。 |

## 已定决策

- **技术栈**：Vite + React + TypeScript，产物 `renderer/dist`（阶段 5 由 Electron `loadFile` 加载）。
- **主题**：DARK 与 LIGHT **都做**，同一套 CSS 变量换值；参考默认 DARK。
- **点阵字体**：Doto（OFL，许可与原文随字体放在仓库里）。
- 口播与 UI 文案**英文**；项目文档中文。
- 只做 **PC 单端**（ADR-0007）：无账号、无输出设备选择、server 只绑 `127.0.0.1`。
- 界面唯一真相是 `shared/api-types.ts`；UI 只认 HTTP + WS（铁律 5）。
- base URL 与 token **只在一处注入**，切真后端只改这一个值（ADR-0006）。
- 音频真的用 `<audio>` 播；口播用 `<audio src="/tts/<hash>.mp3">`。
- `HIDE` / `LIST` 保留，它就是 QUEUE 区的折叠开关（参考里是同一个按钮的两个标签）。

## 交互决策（用户已逐条确认）

1. **点 QUEUE 某一行 → 切到那首歌**（不是「加入队列」）。
2. **`♡` 与 `FAV` 是两个入口**：`♡` 喜欢/取消喜欢**当前这首**；`FAV` 打开**喜欢列表**。
3. **DJ 消息里的曲目卡，点一下就播放**。
4. **v1 不做语音输入**：麦克风按钮只作外观，只保留文字输入。
5. **`LOGIN` 保留，而且它不是装饰**：点开是一个**凭证弹窗**，填 LLM / TTS 的 API key 与网易云 cookie。
6. **QUEUE 面板有两种来源**：`AI 推荐` 与 `FAV`，**在同一块面板里切换**。点 `FAV` 就是把面板里的歌换成喜欢列表，再点一次切回。
7. **喜欢列表的增删**：增＝播放器上的 `♡`；删＝行内 `✕`（设计见上）。

## 需要后端提供的新契约面（已冻结）

现有的契约（`shared/api-types.ts`）原本**没有**喜欢这条线，也**没有**说清「谁决定现在播哪首」。
按铁律 3（冻结契约 → mock → UI），这两件事在动 UI 之前定掉了 —— 见
[ADR-0010](../adr/0010-playback-authority-and-favorites.md)。
**下表 P1–P4 已全部落地，UI 可以直接照着写。**

| # | 提案 | 形状 | 为什么是这个形状 |
|---|---|---|---|
| P1 | 读喜欢列表 | `GET /api/favorites` → `TrackRef[]` | 和 `GET /api/next` 同构，UI 复用同一套行渲染 |
| P2 | 喜欢 / 取消 | `POST /api/feedback` `{ songId, action: 'like' \| 'unlike' }` → `OkResponse` | 和已有的 `POST /api/playback` 同构（都是「客户端报告一个事实」）；`action` 是**封闭枚举**，将来要加 `dislike` 只是加一个值 |
| P3 | 队列跳播的语义 | 不新增端点：`POST /api/playback { event: 'started' }` **同时**是「我切到这首了」的宣告 | ADR-0007 已经定了「PC 端由渲染进程直接播放」，所以**播放权威在客户端**。点 QUEUE 某行、点曲目卡、点 `⏭`，都是客户端换 src 后上报；server 据此更新 `now` 并在 WS 上推 `now`。把「命令」和「报告」合成一条，是为了不让两边各说各话 |
| P4 | DJ 详情里的曲风胶囊 | `TasteDoc` 加一个 `genres: string[]` | 这几个胶囊是**数据**不是写死的字符串，否则「taste」就变成了装饰 |
| P5 | 凭证（`LOGIN` 弹窗） | `SettingsView.music: { provider, cookieSet: boolean }`；`SettingsInput.music?: { provider?, cookie? }` | **现在没有任何地方能存网易云 cookie。** 沿用已有的「key 只回显配没配」模式，`MUSIC_U` 永不回显（危险字段禁令） |

P1–P4 一次落地：`shared/api-types.ts` 一改就是 ADR 级（ADR-0006），所以四条合成一个 ADR-0010，
连同 `shared/ports.ts` 的 `Store.favorites()` / `Store.setFavorite()`、mock 的两个路由、4 条契约测试一起进。
P3 的落地形态是**注释与语义**（不新增端点），落在 `PlaybackReport` 上。
P4 / P5 分别落在 [ADR-0010](../adr/0010-playback-authority-and-favorites.md) 与 [ADR-0011](../adr/0011-music-credential-in-settings.md)。

## 3.6 落地记录（PR #16）

这一节只记「实现把规格落成了什么」，规格本身不动。

### 基准尺寸定案

**616 × 876**，由用户答复给出（他手里有参考源口播卡片的真值）。整块画布按
`min(窗口宽/616, 窗口高/876)` 等比缩放，**布局一行不折**：CSS 里再也搜不到 `media query`。

缩放比例只能在 JS 里算一次（`scale()` 只吃无单位数，`calc(100vw/616)` 是长度），
写到 `--scale`，CSS 只负责吃它。副作用是 `transform` 换了子元素的包含块：
**覆盖层必须挂在 `.stage` 内部**，`position: fixed` 在缩放后会飘出画布。

### 配色改为逐像素采样（覆盖「设计 token」表）

上一版 token 是从截图目测的。这次直接读参考源截图像素，实测值：

| 位置 | 采样 | 结论 |
|---|---|---|
| light 模式强调色（ON AIR 那一点） | `#2ffdb4` | 与 dark 的 `#29FFB8` 同一个绿 → **两态同值**，浅底上不必调暗 |
| light 模式圆形运输键区域（最深像素） | `#565656` | 参考在浅底上**没沿用深色实心圆键**，是描边灰 → light 的 `--btn` 是 `transparent` |
| light 模式画布 / 面板 / 大钟面板 | `#fbfbfa` / `#ffffff` / `#f4f4f3` | 三者不同，大钟面板略深一点 |
| dark 底 / 面板 / 大钟面板 | `#0b0b0d` / `#101013` / `#0d0d10` | — |

另外补了一个 token：`--pill-line`。`HIDE` / `FAV` / `LOGIN` 的描边原来取 `--line`，
压在面板色上几乎看不见 —— 这是并排看截图才发现的，读代码发现不了。

### 本轮我定的两处文案（用户可否决）

| 位置 | 我定的 | 理由 |
|---|---|---|
| DJ 详情页脚 | `EDGERUNNER × TASTE.MD` | 参考是 `CLAUDIO × 作者名`；我们只有一个使用者，就把署名指向 taste 语料 —— 和上面那行「会打碟的taste.md」咬合 |
| 我的消息署名 | `ME` | 参考里是使用者的昵称；v1 只服务一个人，写死 `ME` 反而诚实 |

口号 / 署名 / 座右铭 / 三项统计保持原定稿，一个字没动。

### 曲目卡挂在哪（约定，不是契约）

DJ 消息里的曲目卡挂在 `DjMessage.meta.tracks` 上。`meta` 本来就是
`Record<string, unknown>`，所以没动 `shared/api-types.ts`，也就不需要开 ADR（铁律 3）。

实现上不赌「HTTP 和 WS 谁先回来」：两条路径都调同一个幂等的 `withCards()`
（详见 `docs/journal/2026-10-20.md` 里记的那个 bug）。

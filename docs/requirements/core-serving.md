# 需求：电台状态机与 HTTP/WS 服务（`core/radio.ts` + `core/server.ts`，阶段 4.5）

> 铁律 2 的产出。回答"内核最后一块被要求做什么"：谁拥有电台的状态、谁推进播放、坏了怎么办。
> 契约（路径 + 字段名）在 `docs/abstraction-layer.md` 第 5 节，已冻结；本文件只管分工与失败语义。

## 目标

把 4.1–4.4 的零件（存储 / 大脑 / 音源 / 嗓子）装成一台**电台**，并把它翻译成第 5 节契约里的
HTTP + WS 端点。装完之后，`renderer/` 只需要把 base URL 从 mock 换成它，**UI 一行不改**（铁律 3）。

## 两条纪律

- **状态只有一处**：`core/radio.ts` 拥有"现在放的是哪首、DJ 在不在说话、队列是什么"。
  `core/server.ts` **不持有任何状态** —— 它只把 HTTP/WS 翻译成对 radio 的调用。
- **只绑 127.0.0.1** + `x-radio-token`（ADR-0007：单端，只服务本机）。令牌挡住浏览器里别的页面误打这个端口。

## 播放的三种推进（分工是硬的）

| 推进 | 谁发起 | 做什么 |
|---|---|---|
| 开机 | 自己（`boot()`） | 一次 `think('schedule')` —— "一开机我就打碟" |
| 一首**自然放完** | **服务端** | 客户端 `POST /api/playback {event:'ended'}`。队列没到底 → 自己走一格（不问大脑、不花钱）；队列到底 → 才 `think('track_end')` 换一批 |
| 用户**切歌** | **客户端** | 客户端自己切（点队列行 / 点曲目卡 / 点下一首），再 `POST {event:'started'}` 宣告。服务端只记账并更新 now（ADR-0010） |

要点：`event:'started'` **同时**是"我切到这首了"的宣告，所以没有单独的"跳播"端点。
`POST /api/chat` 立刻回一段 `Show`，音频在后台一句句到 —— 逐句推是**流**的事，不是这次 POST 的事。

## 事件与快照（`WS /stream`）

- 六种事件：`now` / `say` / `queue` / `plan` / `state` / `error`，只从 radio 出。
- 连上先给一份快照（`now` + `queue` + `state`），UI 不必先轮询一轮。
- socket 是**单向** server → client（只发不收）。手写握手，按 RFC 算 `Sec-WebSocket-Accept`。

## 坏了怎么办（抽象层第 6 节的落地）

- **没有 LLM key**：只降口播，不降音乐。发 `NO_LLM_KEY` 事件，队列**自己走**。唯一例外是 `chat`
  —— 没有大脑就是没有答案，回 503 `NO_LLM_KEY` 比假装在想要诚实。
- **单句 TTS 失败**：发 `TTS_FAILED` + 给一条"有字没声"的兜底 `SpokenLine`（词表退化成覆盖全句的一个词），
  **继续下一句**。整条口播消失比"有字没声"更糟。
- **音乐解析不出来**：`MUSIC_NOT_RESOLVABLE`。链把"源不可达"和"解析不出来"都收敛成 null（ADR-0016 的既定取舍）。
- **错误码是封闭枚举**：未知路由 / 参数不合法也用 `INTERNAL`，不为它们开新的错误码。

## 降级是**推断**出来的，不是记一个布尔

`NowPlaying.degraded` = 队列非空且**每一首**的源都是 `local`。

- 为什么不记一个"我降级了"的开关：那个开关会有第二个写入口，两个入口就会打架。
- 为此 radio 维护一个小目录 `catalog`：从**工具结果**里捡完整 `Track`，给队列里的 `TrackRef` 补 `source`。
  v1 没有 songs 表，这不是歌曲库，是"这一阵子见过的东西"。

## 媒体路径（两条豁免）

- `/api/audio/:songId` → **302 到远端 URL**，不反向代理（ADR-0018）。
- `/tts/<40位hex>.mp3` → 从口播缓存直接给字节，支持 `Range` / `206` / `416`（`<audio>` 会拉 Range）。
- 这两条**豁免令牌**：`<audio>` 设不了自定义头，也不该被业务错误拦住。

## 设置与凭据

- `PUT /api/settings` 写封闭 key；**空字符串 = 不改**，所以 key / cookie 不可能被一次空提交清掉。
- 回显只有 `apiKeySet` / `cookieSet` 两个布尔，明文 key、整条 cookie **永不出现在任何响应里**（ADR-0005 / ADR-0011）。
- 设置一变（按 key 集合的 sha1 签名比对）就**重建** provider —— 这就是"填了 key 立刻生效"，
  也是 key 唯一流进 provider 的地方。

## 日表（`core/plan.ts`）

- 三个时段**写死在代码里**（07:00–12:00 morning / 12:00–18:00 daytime / 18:00–02:00 late-night），
  理由和 systemPrompt 一样：它是产品的脾气（什么时候该是什么氛围），不是运维参数。
- 每格里的曲目是**尽力而为**的推荐：拿不到就留空数组。日表里没歌不影响电台工作 —— 下一首播什么由大脑现场决定。

## 明确写下来的假设

- **假设 1**：只有一个渲染进程连它（ADR-0007），所以"订阅者集合"是个 `Set`，不做多端一致性。
- **假设 2**：`Clock` 注入（`shared/ports.ts` 3.6）。`core/` 里不出现 `new Date()` —— 否则调度器没法测。
- **假设 3**：catalog 是"见过的曲目"，不是权威曲库。它 miss 时 `source` 记 `'unknown'`，不编一个源出来。
- **假设 4**：`agents/` 里的 weather / calendar 端口 v1 恒空（`weather → null`、`calendar → []`），
  prompt 里少一段上下文而已，不影响开机。

## 明确不做

- 不做多端 / 局域网分发（ADR-0007）、不做硬件（ADR-0002）。
- 不做"跳播"端点：切歌是客户端的事（ADR-0010）。
- 不做服务端播放队列的权威：服务端不猜客户端在放什么，只记账。
- 不做歌词（ADR-0009）。
